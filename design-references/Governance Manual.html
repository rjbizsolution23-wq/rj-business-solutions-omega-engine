01The 4 principles.

The rules of the road for anyone touching the RJ Brand OS. If a decision doesn't fit here, escalate. When in doubt, ship the smaller change and review.

● Principle 01 · Ownership

Every asset has one owner. Full stop.

An asset without an owner drifts. A shared asset drifts twice as fast. Every design surface — from a token to a screen — has a single named owner accountable for its correctness, versioning, and deprecation.

Owners can delegate execution but never delegate accountability. If a client sees a broken chart, we know who to call.

Rule · Every entry in the asset registry has an owner field. Missing owner = missing asset.
● Principle 02 · Versioning by intent

Version numbers signal user impact — not effort.

We use semantic versioning for brand assets, adjusted for design intent. Major means visible change users will notice. Minor means additive capability. Patch means invisible correction.

If a change moves any pixel a user has seen, it's at least minor. Only refactoring gets called patch.

Rule · Never break a public URL. Move to a new version file. Keep the old file live for one release cycle minimum.
● Principle 03 · Approval by risk tier

Green auto-ships. Yellow logs. Red stops.

Not every change needs a meeting. Not every change should skip one. We tier changes by blast radius — cosmetic staging changes ship autonomously, revenue-critical production surfaces get an explicit gate.

Default posture: build. Approval only inserts itself where the cost of getting it wrong is high enough to earn a delay.

Rule · Two tiers by default: build (autonomous) vs hard stop (owner approval). Yellow tier exists only for changes that need retroactive audit.
● Principle 04 · Deprecation before deletion

Assets retire gracefully — they don't disappear.

The moment an asset is marked deprecated, three things happen: the asset registry flags it, dependent assets get review notices, and the successor is documented in the header. Nothing gets deleted for at least one release cycle.

This is how we avoid the "why doesn't this component work anymore" crisis every design system eventually has.

Rule · Deprecated assets stay accessible for 90 days minimum. Deletion requires explicit owner approval + dependency check.

04Versioning & lifecycle.

Every asset moves through five states. The state is stored in the asset registry alongside the semver version. Never deploy anything that isn't at least Approved.

01
Draft

Being built. Not linked from anywhere public. Owner iterating.

02
In review

Ready for owner + steward sign-off. Approval gate active.

03
Approved

Cleared to ship. Linked from index. Registry entry created.

04
Production

Live. In use by clients or team. Changes require versioning.

05
Deprecated

Successor documented. 90-day grace period before deletion review.

● Versioning rules · always

Semver, adjusted for design.

MAJOR (1.x.x → 2.0.0) — any visible change users will notice. Breaking a public URL. Changing a token users have consumed downstream. New signature on a component. Requires full lifecycle: draft → review → approved.

MINOR (1.0.x → 1.1.0) — additive capability. New variant of a component. New state added to system-states library. New chart type in data-viz library. Backward compatible.

PATCH (1.0.0 → 1.0.1) — invisible correction. Fixing a spacing typo. Correcting a color hex that was off from the token. No user-facing change.

06Deprecation protocol.

The retirement pipeline. Assets don't get deleted — they get gracefully retired with successors documented and dependencies flagged for update.

01

Mark deprecated in registry

Owner flags the asset as deprecated in manifest.json. Timestamp logged. Successor URL required if one exists.

Day 0
02

Dependency scan runs

Every asset that references the deprecated one is auto-flagged for owner review. Reviewers see "uses deprecated · action needed by Day 30".

Day 0
03

Deprecated banner surfaces

Any user viewing the deprecated asset sees a soft banner: "This is superseded by [successor]. Retiring in 90 days."

Day 0-90
04

Dependencies migrated

All dependent assets updated to new successor. Registry entries updated. Old references become soft aliases.

Day 1-30
05

Grace period

90 days minimum. Deprecated file remains accessible. Analytics track usage to confirm safe to retire.

Day 0-90
06

Retirement review

Owner + Steward review usage data. If <5 hits/month over grace period, retire. Otherwise extend for another cycle.

Day 90
07

Archive · never delete

Retired files move to /archive/ with metadata preserved. Registry marks status archived. Rick approval required to permanently delete.

Day 90+
